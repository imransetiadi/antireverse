# Slice 20 — Exposure: Virtual Patches Implementation Plan

> **For agentic workers:** implement task by task, test first. Each task is owned by one worker and touches only its own workspace. A task is finished only when its verification commands were run and their output read. CLAUDE.md Rule 1 applies: on a real design fork, implement the plan as written and list the fork in your report — do not decide it.

**Goal:** A known exploit request for a vulnerable package is recorded, then refused once enforced, only where that version runs.

**Architecture:** Protocol defines the patch schema, the condition language and a reference matcher. The API holds the catalog, decides which patches are active per App and Environment from Findings, stores the admin's mode, ships active patches in the signed bundle and opens Incidents. Shield evaluates header, path and query conditions at decision time and body conditions in `verifyBody`. The Console shows patches on the Finding page and the Policy page. No new dependency.

**Spec:** [tickets/20-virtual-patches.md](../tickets/20-virtual-patches.md); PRD FR-EXP-05; SDD §12A; earlier plans bind (slice 02 rules, broad-rule confirmation, monitor never changes a response; slice 04 `verifyBody`, `bodyVerified.types`, `errorHandler`, fail closed only where enforced; slice 06 Incidents and alerts; slice 19 Findings; D-004 fail open; D-053 design; never log bodies, header values or query values).

## Global Constraints (additions)

- **Patch id:** `vp_<slug>` matching `^vp_[a-z0-9_]{3,48}$`; stable across catalog versions.
- **Patch (catalog entry):** `{ id, title (≤ 120), advisories: [1–10 CVE/GHSA ids], package (npm name), methods?: [...], path?: glob (rule glob syntax), conditions: [1–8], reference: { exploit: Request, benign: Request } }` where `Request = { method, target, headers?, body?, content_type? }`.
- **Condition:** `{ target, name?, op, value? }`.
  - targets: `method`; `path` (Shield's decoded, dot-resolved path); `query_key` (any key of the query, decoded); `query_value` (`name` given → that key's values, else any value); `header_name`; `header` (`name` required, lower-case; value); `body` (raw body bytes as UTF-8, only through `verifyBody`).
  - ops: `equals`, `contains`, `starts_with`, `ends_with`, `length_over` (value = decimal 1–1,000,000), `present` (no value).
  - Comparison is ASCII case-insensitive; values 1–256 chars; strings compared on the decoded form and on the raw form (a match on either counts), with decoding bounded (one pass of percent-decoding, `+` as space in queries).
  - All conditions must hold. A patch with a `body` condition is "body-dependent".
- **Cost:** per request at most 50 patches × 8 conditions; no regular expressions; each condition linear in its input; inputs capped (path and query 8 KB, each header 8 KB, body as the parser's limit).
- **Bundle:** new optional member `patches: [{ id, mode: "monitor"|"enforce", methods?, path?, conditions, advisory }]` ≤ 50 (advisory = the Finding's advisory that activated it). Older Shields strip it.
- **Event:** `decision.patch_id` optional-nullable (default null). A patch decision: action block, mode as shipped. Order: containment, then rules and signature rules (slice 04 order), then patches; the first enforced match wins; monitor matches are recorded only if nothing else decided.
- **Body-dependent patches:** non-body conditions checked at decision time; if they hold, `verifyBody` checks the body conditions. Under enforce a full match throws the slice 04 403 error (rendered by `shield.errorHandler()`). If the body was never checked (no hook, or type not in `bodyVerified.types`), the Event records the patch with `body: "unchecked"` and the request passes (fail open; never blocks).
- **Activation:** a patch is active for (Org, App, Environment) when a Finding there with status open or ignored has an advisory id (or alias) in the patch's `advisories` and the Finding's package equals the patch's package. Default mode monitor. Mode stored per (Org, App, Environment, patch) and kept when the patch drops out and comes back.
- **API:** `GET /v1/apps/:appId/patches?environment=` → `{ patches: [{ id, title, advisories, package, mode, active, findings: [ids], hits_24h, last_hit }] }` (admin); `POST /v1/apps/:appId/patches/:patchId/mode { environment, mode, confirm: "<patch id>" when going to enforce }` → updates and re-issues the bundle. Activation changes (Finding opened, fixed, withdrawn) re-issue the bundle the same way Containment changes do.
- **Incident:** rule `exploit-attempt` (title "Exploit attempt", High, threshold 1), grouped per (App, Environment, advisory) while open/acknowledged; `advisory_id` set; alerts through the notifier.
- **Console:** Finding page section "Virtual patch": available or none; mode chip (Monitor/Enforce); hits in 24 h; "Enforce" (typed confirmation of the patch id) and "Back to monitor"; note "A patch blocks known exploit requests. Upgrading is the fix." Policy page section "Virtual patches" listing active patches with mode and hits. Event/feed decision shows "Patch: <title>".
- **Catalog:** `apps/api/src/patches/catalog.ts` (data) behind a `PatchCatalog` dependency; a fixture catalog for tests. First entries chosen from well-known npm advisories with request-level exploits (candidates: qs prototype pollution through query keys, CVE-2022-24999; lodash prototype pollution through JSON keys, CVE-2019-10744 / CVE-2020-8203; xml2js prototype pollution through XML elements, CVE-2023-0842). Every advisory id is checked against the public OSV API (`https://api.osv.dev/v1/vulns/<id>`) when written — advisory ids only, never customer data — and the affected package and ranges recorded in a pinned test. Each entry's reference exploit must match and its benign request must not (test over the protocol matcher).

## Review Focus

1. **False positives:** benign traffic (JSON with keys like `constructor` in ordinary use, encoded paths) must not match; reference benign requests; monitor never changes a response.
2. **Evasion:** encodings (percent, double, `+`, mixed case, Unicode), duplicate keys, arrays in query, header folding, body content types — matched on decoded and raw forms.
3. **Cost:** no super-linear work; caps hold; bench within PB-01.
4. **Activation and tenancy:** patches only where a matching open/ignored Finding exists in that Org/App/Environment; mode changes audited; confirmations.
5. **Fail-open:** an unchecked body never blocks; internal errors in patch evaluation fail open (no enforced requirement applies to patches).

## Tasks

Order: Task 1 (protocol) → Tasks 2–4 in parallel (API ‖ Shield ‖ Console) → Task 5 (e2e) → Task 6 (review, docs).

## Residual risks known up front

- Exploit variants outside the pattern pass; upgrading is the fix.
- Body conditions need the parser hook.
- A wrong pattern can block benign traffic once enforced — monitor first and reference benign requests reduce this.

## Deliberately not in this slice

Customer-written patches · non-Express adapters · automatic catalog updates · response-side patches.

Not added: cross-field refines on decisions (none exist elsewhere).
- **A2 — Console as built (Jev: accept_fix_env_titles, 0.86).** Finding page "Virtual patch" section (mode chip Monitor eye dashed / Enforce shield-check solid; typed confirmation of the patch id; Back to monitor in one action; "Not shipped: bundle budget"; inactive match shown with a note and no actions; load failure does not break the page); Policy page "Virtual patches" list, read only; feed and Incident evidence show "Patch: <title>" and "body not checked". - **A3 — API as built (Jev: fix_3_4_7_accept_rest, 0.98).** Catalog `2026-11-11.1` verified against OSV: `vp_qs_proto_query_key` (GHSA-hrpp-h998-j3pp / CVE-2022-24999, qs), `vp_lodash_constructor_prototype` (GHSA-jf85-cpcp-j695 / CVE-2019-10744, lodash), `vp_lodash_proto_json` (GHSA-p6mc-m468-83gw / CVE-2020-8203, lodash), `vp_xml2js_proto_element` (GHSA-776f-qx25-q3cc / CVE-2023-0842, xml2js); the catalog refuses an entry whose exploit does not match or whose benign request matches. Migration 0018 (`patch_modes` under RLS; `exploit-attempt` Incidents with `advisory_id`). Bundle re-issued through a patch digest. - **A4 — Changes as built (Jev: accept_actor_only, 0.99).** Exploit Incidents list evidence from Events whose patch covers the Incident's advisory (id or alias) within the Incident's span; Actor blocks work; a prefix block answers "not applicable" (these Incidents have no prefix of their own) and the Console shows it as unavailable. - **A5 — Shield as built (Jev: fix_2_3_5, 0.64).** `src/patches.ts` mirrors the protocol matcher (differential test over 4,000 requests × 12 patches, one and two phases; constants pinned); decision order containment → rules → signature rules → patches; monitor responses byte-identical; the patch 403 reuses the slice 04 error and `errorHandler()`; fail open on internal errors; nothing of headers, queries or bodies logged. The cost bound is measured with 50 × 8 conditions applied in process (the 16 KB budget fits about 50 × 4 in a bundle). Changed: a patch Shield cannot read is skipped and counted instead of refusing the bundle, so a future catalog never stops older Shields from taking rule and Containment updates; body conditions are checked whenever `verifyBody` sees the bytes; an enforce patch whose body was not checked records mode monitor and `patch_body` unchecked.
- **A6 — Review fixes (to do, test first).** F1 (HIGH; Jev decode_utf_fail_closed_rest 0.82; owner chose Block 2026-11-11): bodies are decoded as UTF-8, UTF-16LE/BE or UTF-32LE/BE (charset parameter or BOM) before body conditions; any other charset seen by `verifyBody`, under an enforced body patch whose other conditions hold, counts as a match and is refused (monitor records a match). F2 (HIGH): a body that was never checked is recorded as action allow with `patch_id` and `patch_body` unchecked, and never counts toward `exploit-attempt` or hits. F3–F8 (Jev fix_set 0.91): query pairs split like qs (`]=` first) plus the whole raw segment as a key candidate; extra catalog patches for urlencoded bodies (qs `__proto__` keys; lodash `constructor[prototype]`) and lodash `constructor[prototype]` query keys; no method scope on body patches; new body operator `json_key` (quoted name, optional JSON whitespace, `:`) used by the lodash patches, with benign references holding those words as values and prose; the xml2js patch drops its content-type condition; each decoded form computed once and skipped when identical to raw, body cost documented as linear and benched at 100 KB. Also: an end-to-end case with the real qs patch activated by a Build that ships a vulnerable qs version.
- **A7 — Correction to A6 F3.** The whole raw query segment is NOT a key candidate (it would make values such as `q=__proto__` match a `query_key` condition and break the benign references); keys are taken as qs does (split at `]=` when present) plus the key before the first `=` (older qs). That closes `a[b=c][__proto__]=x`. Jev 0.49 on the alternatives; recorded as a correction of the brief, not a new product decision. A body whose UTF-16/32 encoding is chosen only by a byte order mark is also read as UTF-8, so a fake mark hides nothing.
- **A8 — Catalog after the review (Jev add_path_patch_drop_ct, 0.96).** Unchecked bodies count nowhere (rules, hits, evidence). Added: `vp_lodash_proto_path` (`__proto__.` in a body) and `vp_lodash_constructor_path` (`constructor.prototype`) for CVE-2020-8203 path strings, since `json_key` no longer covers them; the lodash constructor/prototype JSON patch drops its content-type condition.
- **A9 — Matcher after the review (Jev native_indexof_latin1, 0.82).** Built: `json_key` (body only), qs-style key split, UTF-8/16/32 decoding by charset or byte order mark (a mark alone also gets a UTF-8 reading), unknown charsets match under D-062, unchecked bodies recorded as allow, decoded forms computed once. - **A10 — After the fixes.** Native search: a 108 KB body p50 0.41 ms / p99 1.02 ms (was 6.0 / 8.3 ms); adversarial 50 × 8 near-miss conditions on 100 KB 11 ms (was 63 ms). `LATIN1_CHARSETS` exported and pinned.
